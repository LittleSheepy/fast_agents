### 现状（基线：2026-11-04，`9657e7f`）

### 关键设计

**B1 · SessionStore（✅ 已完成，2026-10-29）**

实现落地在 `fast_agents/memory/session_store.py`，含三个对外类：

```python
class SessionStore(ABC):                       # 抽象接口
    def load(self) -> list[Message]: ...
    def append(self, message: Message) -> None: ...
    def clear(self) -> None: ...
    def save_summary(self, summary: str) -> None  # 可选：持久化滚动摘要
    def load_summary(self) -> str

class SQLiteSessionStore(SessionStore): ...    # 零依赖 SQLite 实现（与长期记忆可共用 .db 文件）
class InMemorySessionStore(SessionStore): ...  # 单元测试用
```

`BufferMemory` 新增 `persist_store: Optional[SessionStore]` 参数：构造时 `load()` 回填消息 + 摘要，`append()` 同步落库，`_maybe_compress()` 更新摘要时 `save_summary()`，`clear()` 同步清持久化层。`MemoryManager` 新增 `session_store` 参数透传给 BufferMemory。**上层（ReActAgent）完全不用改**，符合原设计中「上层接口不变」的约定。

落盘表结构（对齐最初设计、并补齐 tool_calls/tool_results/metadata/summary 字段以支持 ReAct 的工具调用链）：

```sql
-- 消息表：自增 seq 保序，避免时间戳同毫秒乱序
sessions(seq INTEGER PK AUTOINCREMENT, user_id, session_id,
         role, content, tool_calls JSON, tool_results JSON,
         timestamp ISO8601, metadata JSON)
-- 摘要/元数据表：滚动摘要单独存，不和消息混
session_meta(user_id, session_id, summary, updated_at,
             PRIMARY KEY(user_id, session_id))
```

作用域隔离与长期记忆保持一致：所有读写都强制带 `user_id + session_id`，杜绝串会话。持久化调用全部包在 `try/except` 里，失败仅打印警告、不中断主流程（与摘要降级策略一致）。

**B2 · 语义检索（✅ 已完成，v1.4.0 / 2026-11-01）**

`memory_store_base.py` 的 `MemoryStoreBase` 接口**未动**（`search()` 默认实现保留纯词法行为），新增 `fast_agents/memory/semantic_store.py`：

- **包装器模式**：`SemanticMemoryStore(inner, llm, *, hybrid_weight=0.7)` 包任意 `MemoryStoreBase` 实例（SQLiteMemoryStore / InMemoryStore / 自定义后端均可），与 inner 组合而非继承；
- **向量存储**：SQLite 后端走同库独立表 `memory_embeddings`（BLOB float32，带 `(memory_id,user_id,session_id)` 主键 + 作用域索引 + 外键级联），InMemory 后端走内存 dict；不污染 `memories` 主表 schema；
- **打分公式**：`relevance = 0.7 × cosine(q,d) + 0.3 × lexical`，外层仍走 `0.6 × relevance + 0.3 × importance + 0.1 × recency`；非偏好类「词法=0 且语义<0.3」过滤；偏好类保底相关度 0.3；排序 tie-breaker `-score → -importance → -updated_at`；
- **降级原则**：`embed_query` / `embed_documents` / BLOB 序列化任何一步失败，一律 `RuntimeWarning` + 退化为纯词法，主流程不中断；
- **懒加载**：旧 SQLite 库升级无需迁移脚本，首次 search 无向量时自动补算写回；提供 `rebuild_embeddings(batch_size=20)` 手动重建；
- **零新增依赖**：标准库 `struct` 序列化 BLOB、纯 Python 余弦相似度，不引 numpy/faiss；
- **验收**：`test_semantic_synonym_recall`（「用户所在地」能召回「我在上海工作」，纯词法召不回）、`test_semantic_graceful_degrade`（embedding 失败不炸、降级纯词法）、`test_semantic_revise_and_crud`（revise/delete/clear 同步清理向量）三项测试通过，合计 memory 模块 14/14 全过。

使用方式：

```python
from fast_agents.llm import LLM
from fast_agents.memory import SQLiteMemoryStore, SemanticMemoryStore, MemoryManager

llm = LLM()
inner = SQLiteMemoryStore("memories.db", user_id="u1")
store = SemanticMemoryStore(inner, llm)          # 默认 hybrid_weight=0.7
manager = MemoryManager(llm=llm, long_term_store=store)
# Manager / Agent / 记忆工具全部不用改
```

> ⚠️ **注意**：`MemoryManager` 的参数名是 **`long_term_store`**（不是 `long_term`）。早期文档与 `semantic_store.py` 文件头注释里曾写过 `long_term=store`，直接复制会触发 `TypeError: __init__() got an unexpected keyword argument 'long_term'`；该缺陷**已修复**——源码 docstring 与文档示例均已在 v1.7.1 / v2.15.0 对齐。下面所有示例均以**正确参数名 `long_term_store`** 为准。

> **命名依据**（保留供后续 aembed* 扩展参考）：LangChain 用 `embed_query` / `embed_documents`；sentence-transformers 用 `encode` / `encode_query` / `encode_document`；BGE / Milvus 用 `encode_queries` / `encode_documents`；OpenAI SDK 靠 `input` 单/批量不分方法。本框架取 **LangChain 方案**——写入知识库走 `embed_documents`（批量、返回 `list[list[float]]`），Agent 检索走 `embed_query`（单条、返回 `list[float]`）。好处是把「单条 vs 批量」「查询侧 vs 文档侧」两个工程差异写进签名，后续接 BGE / E5 / DashScope 这类 query 与 document 需不同前缀或 `input_type` 的模型时，接口无需再改。后续若需异步，再补 `aembed_query` / `aembed_documents`。

**B3 · 结构化用户画像（✅ 已完成，v1.5.0 / 2026-11-02）**

### 关键设计

**K1 · 为什么 trace 要从 infra 中独立成 K 模块（v2.25.0 调整）**：三个动因。①trace 已经有完整的源码目录（`fast_agents/trace/`）、独立的编写说明、独立的测试文件与示例，本质是一个和 tools/memory/llm/database 平级的运行时能力模块，而不是「工程基建杂项」；把它继续挂在 G（infra）会让 G 变成大杂烩，既不便读者定位，也让 G 章节的发包/CI 任务被 trace 喧宾夺主。②与整体模块风格一致——每个"独立目录 + 一份编写说明"的能力单独占一个字母编号（A tools / B memory / C skills / D mcp / E agents / F context / I llm / J database），trace 理应有自己的字母。③K 紧挨着 J（database，K1 直接依赖）排在 LLM/I 之后，语义上也顺手——持久化地基之上是可观测地基，G（infra）留给真正的发包/CI 横切事项。

**K1 · 默认关闭 + 失败安全两条铁律（已落地）**：①框架默认不收集——`ReActAgent(tracer=None)`、`LLM.invoke(tracer=None)` 即零开销、零额外分支；构造出 `TraceLogger` 实例也可以显式 `enabled=False` 整体关闭。②打点通道所有异常一律吞掉——`tool_hook`、LLM 打点、start_span/end_span/write 任何异常只 `logger.warning`，绝不允许 trace 的 bug 变成主业务的 bug。这两条是 trace 作为横切能力的立身之本。

**K1 · 排序与幂等（已落地）**：由于 Windows 下 `time.time()` 精度有限，嵌套 Span 的 `start_time` 可能相同，仅用时间排序会破坏父子顺序；K1 引入全局线程安全自增序号 `_create_seq`，新建 Span 时把序号存进私有属性、以独立 `create_seq` 键/列随 Span 落盘、读回时经 `model_validate(context=...)` 注入私有属性（不写也不读用户 `metadata`），`replay()` 排序键统一为 `(_create_seq, start_time, span_id)`，跨平台稳定。`end_span` 通过 `span._persisted = True` 做幂等标记，异常路径上被重复调用不会重复写入、也不会出现 `status=success` 与 `status=error` 的矛盾记录。

**K1 · 耗时口径抗墙钟跳变（已落地）**：`start_time` / `end_time` 仍取 `time.time()` 墙钟（用于展示 / 排序 / 落盘），但 `duration_ms` 默认改由 `time.perf_counter()` 单调时钟差值计算，避免系统墙钟在执行期间被 NTP 校正 / 手动改表导致耗时失真或为负。为保持零破坏，只有 `TraceLogger.start_span` 正常创建的 Span 才记录单调时钟起点（`_mono_start` 私有属性，不落盘）；显式传入 `end_time`（后钩子精确对齐）或直接构造的 `SpanRecord` 仍走墙钟差值，与旧版逐字节一致。

**K1 · 存储层抽象（已落地）**：`TraceStoreBase` 是抽象基类（对齐 `DatabaseClientBase` 风格），默认落点是 `InMemoryTraceStore`（纯内存，`TraceLogger()` / `store=":memory:"` 用），文件后端 `JsonlStore` 最轻量、零依赖、适合单机脚本，结构化后端 `SQLiteStore` 复用 J 模块 `database.SQLiteClient`（适合生产查询与分析），按文件后缀自动识别（`.db/.sqlite/.sqlite3` → SQLiteStore，其余 → JsonlStore，`:memory:` → `InMemoryTraceStore`）。未来 K5 的 OTel/Langfuse Exporter 也以 `TraceStoreBase` 子类形态接入，门面 `TraceLogger` 零改动。

**K2 · 异步为什么排在后面**：当前 ReActAgent 主循环是同步模型（A26 多工具并发、I2 `ainvoke` 都未落地），先在同步模型下把排序、幂等、落盘安全、LLM/Agent/tool 接入打磨稳，再做 async 适配——避免同时引入两个大改动互相干扰。K2 启动的前置是 A26（Agent 多工具并发）与 I2（LLM async 方法）落地。

**K3/K4/K5 的依赖关系**：K3 评估工具只读 trace 数据做离线统计/打分、不要求实时上报，可先于 K5 落地；K4 Web UI 主要消费本地 store 数据，也可独立落地；K5 外部上报是与外部平台对接的可选能力，优先级最低、且必须作为 extras 依赖、不增加默认安装体积。

### 关键设计

**初版 · 为什么 database 要独立成模块而不是继续放在 memory/infra 里**：三个动因。①**K1 TraceLogger 落盘**会直接依赖 SQLite 存结构化 trace，如果没有独立 database 模块，trace 就得要么自己手写 sqlite3 连接，要么反向依赖 memory 模块——前者和 memory 重复写建表 SQL，后者产生不合理的反向依赖。②**J3 跨模块迁移**要求把 memory 里三个 SQLite 后端的重复建表、迁移、PRAGMA 样板收口，database 独立成模块是这个重构的前提。③**与整体模块风格一致**——memory/tools/mcp/skills/context/llm 每个都是"独立目录 + 一份编写说明"的模块，database 作为全框架底层持久化能力，符合这个独立模块的约定。

**初版 · 三种建表写法并存的取舍**：dict（最快写原型）/ `list[Column]`（声明式带约束和单列索引）/ `Schema`（工程化带复合索引和 migrate）。不强制统一一种风格是因为不同场景成本不同——快速脚本一行 dict 就够，生产表用 Schema 才值得；三种写法底层都走同一个 `CREATE TABLE` 生成函数，对外零认知负担。

**初版 · 标识符白名单而非参数化**：SQL 标识符（表名/列名/索引名/order_by 字段）**不能**用 `?` 参数占位，必须字符串拼接。为了从源头堵注入，所有标识符走正则 `^[A-Za-z_][A-Za-z0-9_]*$` 白名单校验，不合法直接抛 ValueError；值参数仍然全部走 `?` 占位，不拼字符串。

**初版 · 为什么 migrate 是 opt-in（`migrate=True` 才补列）**：默认「只建不改」最安全——不该因为一次 `ensure_schema` 就静默改线上库结构；要自动补列必须显式传 `migrate=True`，且 SQLite 只允许 `ALTER TABLE ADD COLUMN`，NOT NULL 新列必须给 default，否则会明确报错而不是静默失败。drop column / rename column 这类破坏性迁移永远不自动做，必须用户手写 SQL 迁移脚本。

**初版 · 为什么不引入 SQLAlchemy**：呼应全框架"零重型依赖"的设计取舍——只引一个 pydantic（已是全框架基础依赖）+ 标准库 sqlite3，完整 DDL/CRUD/事务 33 项测试全绿代码量不到 500 行；SQLAlchemy Core 能做的事（声明式 schema、类型映射、DDL 生成、事务）初版已经覆盖，为了一个抽象层引入 10MB+ 依赖不值当。未来真要多后端时（J4），要么自己在 `DatabaseClientBase` 下加 MySQL/Postgres 实现（复用 Schema 模型、每个后端 200~300 行），要么再评估是否引 SQLAlchemy 作为可选 extra。

**J7 · 为什么要给 `Query.filters` 补 OR / 嵌套**：关系型与向量两套过滤模型出现了能力落差——`VectorFilter` 已经支持 `op=AND/OR + filters` 嵌套（元数据过滤的常见需求，见 `vector_query.py`），而 `Query.filters` 至今只能传一串平铺叶子条件、顶层隐式 AND，遇到「a=1 或 b=1」这类条件只能退化成裸 SQL `db.execute()`。落地思路：给 `Filter` 增加可选的「逻辑分组」形态（AND/OR + 子条件列表 `children`），叶子的 `field` / `op` / `value` 语义保持不变；SQLite / MySQL 两个后端把编译函数由「逐个叶子拼接」改为「递归下降」，分组外层加括号以保证与顶层 AND 正确结合，值仍全部参数化（占位符统一编号）、标识符仍走白名单；顶层 `filters` 保持隐式 AND 以向后兼容既有调用。
