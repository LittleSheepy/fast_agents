## 四、模块 A：tools（工具系统）

### 现状（基线：2026-11-04，`9657e7f`）

- 基类统一命名为 **`ToolBase`**（**注意不是 `BaseTool`**），入参模型字段统一为 **`args_schema`**（pydantic `BaseModel`，旧版叫 `param_model`），调用入口统一为 **`invoke(tool_input=None, **kwargs) -> ToolResult`**，支持 dict / JSON 字符串 / kwargs 三种传参形式；
- 返回值统一为 **`ToolResult`**（`ok` / `fail` / `truncated` 三态 + `artifact` 结构化副产品），不再有「裸字符串返回」兼容路径；
- 注册表统一入口 **`ToolRegistry.invoke_tool(name, tool_input, **kwargs)`**，返回 `ToolResult`；旧的 `execute_tool`（返回字符串）已删除；
- 单个工具导出 `to_openai_tool / to_anthropic_tool / to_gemini_tool`，批量导出 `to_openai_tools / to_anthropic_tools / to_gemini_tools`；
- 参数 schema 从 pydantic `args_schema` 或函数签名内省生成，嵌套 `BaseModel` / `Enum` 的 `$ref` 会递归内联（OpenAI/Anthropic 不支持 `$defs`）；
- 四种定义方式齐备：继承 `ToolBase` / `@tool` 装饰器 / `StructuredTool.from_function` / 裸函数直接注册；

- 同步/异步双入口 `invoke / ainvoke`；hooks：`_before_run / _after_run / _on_error`，注册表级 `add_hook`；`tags / metadata / return_direct / max_output_chars / handle_tool_error` 配置齐全；
- Agent 侧感知 `ToolResult.status`：ERROR 前缀提示模型重试、TRUNCATED 自带「请缩小查询范围」提示。

### 关键设计

**B1 · SessionStore（✅ 已完成，2026-10-29）**

实现落地在 `fast_agents/memory/session_store.py`，含三个对外类：

```python
class SessionStore(ABC):                       # 抽象接口
    def load(self) -> list[Message]: ...
    def append(self, message: Message) -> None: ...
    def clear(self) -> None: ...
    def save_summary(self, summary: str) -> None  # 可选：持久化滚动摘要
    def load_summary(self) -> str

class SQLiteSessionStore(SessionStore): ...    # 零依赖 SQLite 实现（与长期记忆可共用 .db 文件）
class InMemorySessionStore(SessionStore): ...  # 单元测试用
```

`BufferMemory` 新增 `persist_store: Optional[SessionStore]` 参数：构造时 `load()` 回填消息 + 摘要，`append()` 同步落库，`_maybe_compress()` 更新摘要时 `save_summary()`，`clear()` 同步清持久化层。`MemoryManager` 新增 `session_store` 参数透传给 BufferMemory。**上层（ReActAgent）完全不用改**，符合原设计中「上层接口不变」的约定。

落盘表结构（对齐最初设计、并补齐 tool_calls/tool_results/metadata/summary 字段以支持 ReAct 的工具调用链）：

```sql
-- 消息表：自增 seq 保序，避免时间戳同毫秒乱序
sessions(seq INTEGER PK AUTOINCREMENT, user_id, session_id,
         role, content, tool_calls JSON, tool_results JSON,
         timestamp ISO8601, metadata JSON)
-- 摘要/元数据表：滚动摘要单独存，不和消息混
session_meta(user_id, session_id, summary, updated_at,
             PRIMARY KEY(user_id, session_id))
```

作用域隔离与长期记忆保持一致：所有读写都强制带 `user_id + session_id`，杜绝串会话。持久化调用全部包在 `try/except` 里，失败仅打印警告、不中断主流程（与摘要降级策略一致）。

**B2 · 语义检索（✅ 已完成，v1.4.0 / 2026-11-01）**

`memory_store_base.py` 的 `MemoryStoreBase` 接口**未动**（`search()` 默认实现保留纯词法行为），新增 `fast_agents/memory/semantic_store.py`：

- **包装器模式**：`SemanticMemoryStore(inner, llm, *, hybrid_weight=0.7)` 包任意 `MemoryStoreBase` 实例（SQLiteMemoryStore / InMemoryStore / 自定义后端均可），与 inner 组合而非继承；
- **向量存储**：SQLite 后端走同库独立表 `memory_embeddings`（BLOB float32，带 `(memory_id,user_id,session_id)` 主键 + 作用域索引 + 外键级联），InMemory 后端走内存 dict；不污染 `memories` 主表 schema；
- **打分公式**：`relevance = 0.7 × cosine(q,d) + 0.3 × lexical`，外层仍走 `0.6 × relevance + 0.3 × importance + 0.1 × recency`；非偏好类「词法=0 且语义<0.3」过滤；偏好类保底相关度 0.3；排序 tie-breaker `-score → -importance → -updated_at`；
- **降级原则**：`embed_query` / `embed_documents` / BLOB 序列化任何一步失败，一律 `RuntimeWarning` + 退化为纯词法，主流程不中断；
- **懒加载**：旧 SQLite 库升级无需迁移脚本，首次 search 无向量时自动补算写回；提供 `rebuild_embeddings(batch_size=20)` 手动重建；
- **零新增依赖**：标准库 `struct` 序列化 BLOB、纯 Python 余弦相似度，不引 numpy/faiss；
- **验收**：`test_semantic_synonym_recall`（「用户所在地」能召回「我在上海工作」，纯词法召不回）、`test_semantic_graceful_degrade`（embedding 失败不炸、降级纯词法）、`test_semantic_revise_and_crud`（revise/delete/clear 同步清理向量）三项测试通过，合计 memory 模块 14/14 全过。

使用方式：

```python
from fast_agents.llm import LLM
from fast_agents.memory import SQLiteMemoryStore, SemanticMemoryStore, MemoryManager

llm = LLM()
inner = SQLiteMemoryStore("memories.db", user_id="u1")
store = SemanticMemoryStore(inner, llm)          # 默认 hybrid_weight=0.7
manager = MemoryManager(llm=llm, long_term_store=store)
# Manager / Agent / 记忆工具全部不用改
```

> ⚠️ **注意**：`MemoryManager` 的参数名是 **`long_term_store`**（不是 `long_term`）。早期文档与 `semantic_store.py` 文件头注释里曾写过 `long_term=store`，直接复制会触发 `TypeError: __init__() got an unexpected keyword argument 'long_term'`；该缺陷**已修复**——源码 docstring 与文档示例均已在 v1.7.1 / v2.15.0 对齐。下面所有示例均以**正确参数名 `long_term_store`** 为准。

> **命名依据**（保留供后续 aembed* 扩展参考）：LangChain 用 `embed_query` / `embed_documents`；sentence-transformers 用 `encode` / `encode_query` / `encode_document`；BGE / Milvus 用 `encode_queries` / `encode_documents`；OpenAI SDK 靠 `input` 单/批量不分方法。本框架取 **LangChain 方案**——写入知识库走 `embed_documents`（批量、返回 `list[list[float]]`），Agent 检索走 `embed_query`（单条、返回 `list[float]`）。好处是把「单条 vs 批量」「查询侧 vs 文档侧」两个工程差异写进签名，后续接 BGE / E5 / DashScope 这类 query 与 document 需不同前缀或 `input_type` 的模型时，接口无需再改。后续若需异步，再补 `aembed_query` / `aembed_documents`。

**B3 · 结构化用户画像（✅ 已完成，v1.5.0 / 2026-11-02）**

和 B2 不同，B3 **不碰检索链路**，只在 `memory/` 里新增一条并行的「档案」通路：

- **数据模型**：`schema.py` 新增 `UserProfile`——顶层只放 `name` / `role` / `location` / `language`，其余稳定信息走 `stable_preferences` / `stable_facts` 两个键值字典（刻意不做白名单、不做嵌套，等真实用一段时间再收紧）；
- **存储抽象**：`profile_store.py` 的 `ProfileStore` 只有 `get` / `merge` / `set_field` 三个动作，`set_field` 带默认实现（`build_field_patch()` 翻译字段路径后走 `merge`），**子类只要实现 `get` + `merge`**；
- **两个实现**：`SQLiteProfileStore(path)` 落独立表 `user_profiles(user_id PK, profile JSON, source, updated_at)`，可与 `memories` / `sessions` 共用同一个 .db；`InMemoryProfileStore()` 供单测，`get()` 返回深拷贝；
- **门面**：`MemoryManager` 新增 `profile_store=` 参数与 `get_profile()` / `update_profile(patch)` / `set_profile_field(field, value)` 三个方法；未配置时读返回**空档案**（不抛异常）、写抛 `RuntimeError`，Agent 侧不用加判空；
- **工具**：`UpdateProfileTool`（`update_user_profile`）由 `build_memory_tools(manager, include_profile=True)` 选择性装配，默认 `False` 仍是三件套；
- **边界**：画像**不进 `memories` 表、不进 `auto_extract` 抽取链、不参与 `retrieve()` 打分**——否则会和已有的 `fact` / `preference` 记录重复召回；
- **注入**：v1.5.0 只交付「存取」层；v1.6.0 起由 **B4 双通道注入**正式把 `profile.to_text()` 拼进 L1 system 末尾（走 `ContextBuilder.build(system_tail=...)`，见下文 B4 设计段）；
- **验收**：`test_profile_merge_and_override`（覆盖式合并 + 非法字段报错）、`test_profile_sqlite_persistence`（落盘 + user 隔离）、`test_profile_manager_integration`（整合 + 未配置降级）、`test_profile_tool`（工具装配 + 失败不抛）四项通过，memory 模块合计 19/19 全过。

**B4 · 双通道注入（✅ 已完成，2026-11-02）**

实现跨 `fast_agents/context/builder.py` 与 `fast_agents/agents/react_agent/react_agent.py`：

- **接口**：`ContextBuilder.build()` 新增可选 kwarg `system_tail=None`，不为空时按 `f"{system_prompt}\n\n{system_tail}"` 拼到 L1 system 末尾；为空/`None` 时 system 字节级保持原样；
- **两条路径都生效**：`enable_context=True` 走 `_fit_context()` → `ctx.build(system_tail=...)`；`enable_context=False` 走 `_inject_profile_to_workspace()` 直接追加到工作区 system 消息末尾；
- **不新建独立层**：画像属于 L1「身份锚点」，追加到 system 末尾仍享受 prompt caching 前缀命中；不放进 L2（避免被当参考信息裁剪）、不放进 L5（避免污染本轮问题）；
- **marker 防叠加**：用固定标题 `## 用户画像（稳定信息，请在回答中始终遵守）` 作为分隔，每次 run 前先 `_strip_profile_block()` 剥掉上一轮追加的旧块再追加新块；`refresh_system_prompt()` 重写 system 时也先剥块；
- **空画像静默**：未配 `profile_store` 或 `profile.is_empty()` 时，两条路径都不追加任何文本，system prompt 字节级一致——由 `test_profile_noop_when_empty_or_unconfigured` 锁死该零侵入承诺；
- **失败降级**：画像读取/渲染异常只打 `⚠️` 警告返回空串，主流程不中断；
- **验收**：`test/test_react_agent.py` 新增 3 项——`test_profile_noop_when_empty_or_unconfigured`（零配置字节级一致）、`test_profile_injected_into_system_tail_non_context_path`（非 context 路径追加 + 跨 run 不叠加 + 改画像后下次生效）、`test_profile_injected_via_system_tail_in_context_path`（context 路径走 system_tail 拼到 L1，不污染 L2/L5，跨 run 不叠加）；全量回归 context 16/16、memory 脚本入口 18 项 / pytest 19 项、react_agent 15/15、tools 14/14、file 13/13、mcp 10/10 全绿。

**B5 · 记忆衰减与合并（✅ 已完成，2026-11-02）**

实现集中在 `fast_agents/memory/`（`schema.py` / `scoring.py` / `memory_store_base.py` / `sqlite_store.py` / `semantic_store.py` / `manager.py` 6 个文件）：

- **新增字段**（`schema.py`）：`MemoryRecord.access_count: int=0`、`MemoryRecord.last_accessed_at: Optional[datetime]=None`；**两列都带默认值**，老数据、`to_dict()`、两个后端、既有测试全不破；`MemoryStatus` 新增第四态 `archived`（低重要度 + 久未命中的归档状态，退出检索但保留可审计）；
- **三个默认实现**（`memory_store_base.py`）：`touch(memory_ids)` 自增 `access_count` + 刷 `last_accessed_at`（**不碰 `updated_at`**，保护时间衰减）、`archive_stale(max_importance=0.3, stale_days=90)` 把「重要度 < 阈值 + 距上次使用超过 N 天」的记忆置 `archived`、`merge_similar(threshold=0.85)` 把相似度超过阈值的记忆两两合并到最重要那条，被合并者转 `superseded` 并在 metadata 写 `merged_into`；另有 `semantic_vectors(texts)` 作为向量能力钩子（默认返回 None）；抽象方法保持 6 个不变；
- **合并相似度口径**：与 B2 的 `hybrid_weight=0.7` 对齐——`0.7×语义 + 0.3×词法`，**后端没装 SemanticMemoryStore 或 embedding 失败时直接退化为纯词法**（不能把"拿不到向量"当 0 代入，否则两条完全相同的记忆也只能打到 0.3 分，永远合并不了）；
- **SQLite 自动迁移**（`sqlite_store.py`）：构造时先 `PRAGMA table_info(memories)` 查已有列，缺两列就 `ALTER TABLE ADD COLUMN`，**幂等可重复执行**——用户无需手动迁移，打开旧 `.db` 自动补齐；`add()` 改成显式列名 INSERT（不按位置），兼容老库列序；`touch()` 显式 override 走裸 `UPDATE SET access_count=access_count+1, last_accessed_at=?`，绝不重写 `updated_at`；
- **语义包装器代理**（`semantic_store.py`）：`semantic_vectors()` 走 `llm.embed_documents` 批量算向量（失败整体返回 None 降级）；`touch()` **显式代理给 `self.inner.touch(ids)`**，避免经包装器默认 `get/update` 走回 SQLite 重写 `updated_at`；
- **Manager 入口**：`MemoryManager.retrieve()` 在返回 top-k 前自动调 `_touch_accessed(records)` 给命中条目记账（失败只 warning 不影响返回）；新增 `compact(*, max_importance=0.3, stale_days=90, similarity_threshold=0.85)` 一个入口跑完「归档 + 合并」返回 `{"archived": N, "merged": M}`，**默认不自动执行**（合并是 O(n²) 两两比较，不适合每轮跑），在会话空闲时或手动 CLI 触发即可；任何步骤失败只 warning 不中断主对话；
- **验收**：`test/test_memory.py` 新增 4 项——`test_touch_records_access`（touch 不刷 updated_at、SQLite/Semantic 两个后端都验证）、`test_archive_stale`（默认阈值不归档、时间倒推/importance 降档才归档）、`test_merge_similar_semantic`（纯词法 + 语义+词法混合、语义缺失退纯词法而不是当 0）、`test_manager_compact_and_retrieve_touch`（端到端：retrieve 自动记账 → compact 归档 + 合并 → 被归档/合并的记录退出 all() 检索、主记录保留）；全量回归 93 项全过。

**B9 · SQLite 后端迁移到 `SQLiteClient`（✅ 已完成，v1.7.5 / 2026-11-04）**

`memory/sqlite_store.py` / `session_store.py` / `profile_store.py` 三个后端不再各自手写 `sqlite3.connect` + `CREATE TABLE` + PRAGMA，统一改走 `fast_agents.database.SQLiteClient`：

- **建表**：`ensure_schema(..., migrate=True)` / `ensure_table` 幂等建表并自动 `ALTER TABLE ADD COLUMN` 补列，取代原来的手写迁移；
- **连接与并发**：`SQLiteClient` 自动 `PRAGMA journal_mode=WAL`（非内存库）+ `busy_timeout`（与构造 `timeout` 同口径）+ `foreign_keys=ON` + 参数化查询 + 标识符白名单，三个后端自动继承——**B9 由此落地**；
- **CRUD**：`select_where` / `select_one_where` 谓词下推、`upsert`、`update_where` + `SqlExpr` 批量自增、`delete_where`、`with db:` 事务；
- **逃生舱**：少数 SQLite 特有写法（`INSERT OR REPLACE`、`revise` 的两步事务）经 `db.execute()` 保留；老库零迁移脚本、读回兼容。

**B14 · `ChromaMemoryStore`（✅ 阶段 1，v1.8.0 / 2026-11-04）**

新增 `memory/chroma_store.py`，与 `SemanticMemoryStore` 平级的「换包装器」选项：`ChromaMemoryStore(inner, llm, *, chroma_client=None, collection_name=None, hybrid_weight=0.7, payload_support=True)`。阶段 1 只交付骨架 + 纯词法降级——不引入 `chromadb` 依赖，`chroma_client=None` 时整类降级为纯词法（等效 `inner` 直通），即便传入客户端也一律 `try/except` 降级、不阻塞主流程；`add / get / all / update / delete / clear / search / semantic_vectors` 与 `SemanticMemoryStore` 行为对齐，B5 的 `touch / revise / retract / archive_stale / merge_similar` 全部代理给 `inner`（Chroma 只作向量索引，不参与记账 / 修订 / 归档 / 合并）；集合名按作用域生成。阶段 2：延迟导入真实接 `chromadb` client（optional-deps）。

### 关键设计

**初版 · 为什么 database 要独立成模块而不是继续放在 memory/infra 里**：三个动因。①**G1 TraceLogger 落盘**会直接依赖 SQLite 存 jsonl/结构化 trace，如果没有独立 database 模块，trace 就得要么自己手写 sqlite3 连接，要么反向依赖 memory 模块——前者和 memory 重复写建表 SQL，后者产生不合理的反向依赖。②**J3 跨模块迁移**要求把 memory 里三个 SQLite 后端的重复建表、迁移、PRAGMA 样板收口，database 独立成模块是这个重构的前提。③**与整体模块风格一致**——memory/tools/mcp/skills/context/llm 每个都是"独立目录 + 一份编写说明"的模块，database 作为全框架底层持久化能力，符合这个独立模块的约定。

**初版 · 三种建表写法并存的取舍**：dict（最快写原型）/ `list[Column]`（声明式带约束和单列索引）/ `Schema`（工程化带复合索引和 migrate）。不强制统一一种风格是因为不同场景成本不同——快速脚本一行 dict 就够，生产表用 Schema 才值得；三种写法底层都走同一个 `CREATE TABLE` 生成函数，对外零认知负担。

**初版 · 标识符白名单而非参数化**：SQL 标识符（表名/列名/索引名/order_by 字段）**不能**用 `?` 参数占位，必须字符串拼接。为了从源头堵注入，所有标识符走正则 `^[A-Za-z_][A-Za-z0-9_]*$` 白名单校验，不合法直接抛 ValueError；值参数仍然全部走 `?` 占位，不拼字符串。

**初版 · 为什么 migrate 是 opt-in（`migrate=True` 才补列）**：默认「只建不改」最安全——不该因为一次 `ensure_schema` 就静默改线上库结构；要自动补列必须显式传 `migrate=True`，且 SQLite 只允许 `ALTER TABLE ADD COLUMN`，NOT NULL 新列必须给 default，否则会明确报错而不是静默失败。drop column / rename column 这类破坏性迁移永远不自动做，必须用户手写 SQL 迁移脚本。

**初版 · 为什么不引入 SQLAlchemy**：呼应全框架"零重型依赖"的设计取舍——只引一个 pydantic（已是全框架基础依赖）+ 标准库 sqlite3，完整 DDL/CRUD/事务 33 项测试全绿代码量不到 500 行；SQLAlchemy Core 能做的事（声明式 schema、类型映射、DDL 生成、事务）初版已经覆盖，为了一个抽象层引入 10MB+ 依赖不值当。未来真要多后端时（J4），要么自己在 `DatabaseClientBase` 下加 MySQL/Postgres 实现（复用 Schema 模型、每个后端 200~300 行），要么再评估是否引 SQLAlchemy 作为可选 extra。
